# 宠物健康平台 MVP 技术方案

## 1. MVP 范围与技术原则

### 当前 MVP 必须实现

- Next.js + TypeScript + App Router 的单体应用。
- 一个浏览器页面和服务端 API。
- 输入校验、结构化结果校验和基本错误处理。
- 一个简单的 AI Provider Adapter，以及不调用真实模型的 Fake Provider 用于测试。
- AI Key 只在服务端读取；MVP 不保存用户健康文本。
- T2 的第一个可运行目标：本地启动项目，浏览器访问页面，调用 `GET /api/ping`，返回 `{"ok":true}`。

### 未来扩展

数据库、登录、健康档案、社区、商城、在线问诊、完整可观测性、完整限流和请求预算、Playwright、复杂的多 Provider 编排以及微服务化，均不属于当前 MVP 必须实现的范围。

## 2. 技术栈

- Node.js LTS：降低个人开发者环境和维护成本。
- Next.js App Router：同时提供页面和 Route Handler，减少项目数量。
- TypeScript 严格模式：尽早发现数据结构错误。
- React + 原生 CSS：满足 MVP 页面需要，不引入 UI 框架。
- Zod：集中定义和校验请求、AI 输出结构。
- Node 内置测试能力或轻量测试运行器：进行单元/API 测试，不依赖真实 AI。
- 浏览器手动验收：MVP 暂不要求 Playwright。

不引入数据库、登录系统、消息队列、缓存、容器编排或构建平台等没有必要的基础设施。

## 3. 整体架构

浏览器页面调用 `/api/health-assessments`，Route Handler 负责输入校验、调用应用服务、校验 AI 输出并返回结果。应用服务通过简单的 Provider Adapter 调用 Fake Provider 或未来的真实 Provider。MVP 不落盘健康文本。

## 4. 前端架构

页面负责表单展示、提交状态、错误提示和结果展示。表单只收集用户输入，不在浏览器端计算风险等级，也不包含疾病关键词规则。结果区域展示摘要、初步风险提示、不确定性、观察建议、就医建议和安全声明。

## 5. 后端架构

Route Handler → Zod 输入校验 → 健康评估应用服务 → 简单 Provider Adapter → Zod 输出校验 → 安全响应。

MVP 只保留必要的超时、异常处理、请求体大小保护、服务端 Key 保护和不记录原始健康文本。observability、完整限流和请求预算放到后续部署阶段。

## 6. 数据存储方案

当前 MVP 无数据库、无登录、无用户身份和无健康文本持久化。可保留 `db/schema.sql` 作为未来数据结构展示，但运行时不连接数据库。

未来若经用户反馈验证确有保存需求，再评估 SQLite 或托管 PostgreSQL；届时必须重新设计隐私、删除、访问控制和数据保留策略。

## 7. AI 调用方案

第一版保留简单的 `AIProvider` 接口和 Fake Provider，避免测试依赖网络或真实模型；不建立复杂的插件系统或多模型编排。真实 Provider 只在服务端调用，API Key 不进入浏览器。

输出结构包含：`summary`、`riskLevel`、`rationale`、`observationItems`、`vetAdvice`、`safetyNotice`。

`riskLevel` 仅表示基于当前输入的“初步风险提示”，不是医学风险评分，也不是疾病诊断。第一版不编造医学阈值、疾病规则或关键词诊断规则；信息不足或模型无法可靠判断时返回“不确定”，并提示咨询兽医。

## 8. API 设计

### `GET /api/ping`

T2 最小闭环接口，返回：

```json
{"ok": true}
```

### `POST /api/health-assessments`

属于后续 MVP 实现，接收宠物基本信息和症状文本，返回上述结构化结果。当前 T2 不实现此接口。

错误约定：输入无效返回 `400`，请求体过大返回 `413`，Provider 超时返回 `504`，Provider 或服务端异常返回 `500`/`502`。MVP 不要求实现频率限流测试。

## 9. 核心模块划分

- 页面模块：表单、状态和结果展示。
- API 模块：Route Handler、HTTP 错误映射。
- 校验模块：请求和输出 Schema。
- 应用服务：组织一次评估流程，不包含 DOM 逻辑。
- Provider 模块：简单接口、Fake Provider、未来真实 Provider。
- 安全模块：安全声明、超时、输入限制和失败兜底。

核心预约/评估逻辑必须与 DOM/UI 分离，便于 Node 内置测试。

## 11. 本地开发与最小可运行闭环

在 `pet-health-platform/` 中执行 `npm install`，再执行 `npm run dev`。浏览器访问首页后，打开 `/api/ping`，确认返回 `{"ok":true}`。这是 T2 的第一个可运行目标；健康评估页面和真实 AI 不属于该目标。

## 12. 测试策略

- 对纯校验、应用服务和 Fake Provider 编写单元测试。
- 对 Route Handler 编写 API 测试，测试成功、输入错误、请求体过大、Provider 超时和异常响应。
- 请求体过大时得到 `413`；MVP 不要求实现频率限流测试。
- 测试不调用真实 AI、不依赖数据库和外部网络。
- 使用浏览器手动验收首页和 `/api/ping`；MVP 暂不引入 Playwright。

## 13. 安全与医疗风险控制

- 明确“不替代兽医诊断”，不输出确诊、处方、药物剂量或自我治疗方案。
- `riskLevel` 只代表初步风险提示，不是医学风险评分。
- 不允许代码自行编造医学阈值、疾病规则或关键词诊断规则。
- 低置信度、输入不足或异常结果必须表达不确定性。
- 高风险、异常加重或无法判断时明确建议咨询或就诊兽医。
- AI Key 只保存在服务端环境变量，输入限制和超时保护必须保留。
- MVP 不保存用户健康文本；日志不得记录原始健康内容。
